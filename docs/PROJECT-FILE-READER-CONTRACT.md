# `project.erksproject` — гурван бүтээгдэхүүний уншигчийн гэрээ

- Огноо: 2026-08-30
- Эзэн: STU (Erk-S Studio) — файлыг бичдэг тал
- Уншигчид: PFA (Platform AutoCAD), PFR (Platform Revit)
- Гарал: `docs/INTEGRATION-AUDIT-ONE-2026-08-23.md` → `ONE-HANDOFF-PRODUCT-FIXES.md`
  (PFA-2 / PFR-2, P1 — «аудитын хамгийн ноцтой чимээгүй эвдрэлийн эрсдэл»)

## Юуны тухай вэ

`project.erksproject`-ийг **зөвхөн Studio бичдэг**. AutoCAD ба Revit хоёр
түүнийг өөрсдийн `JsonElement` уншигчаар нээж, талбарыг **нэрээр нь** сугалж
авдаг. Хоёулаа Studio-гийн төрөл рүү deserialize хийдэггүй.

Үр дагавар нь: **Studio талбарын нэрийг сольвол хаана ч, юу ч алдаа өгөхгүй.**
Талбар олдохгүй → `GetString` хоосон мөр буцаана → холболт чимээгүйгээр
таарахаа болино. Гурван бүтээгдэхүүний build-ийн аль нь ч үүнийг мэдэхгүй.

## Бодит гаралт

Жишиг файлыг **Studio-гийн өөрийн бичигчээр** (`ProjectWorkspaceStore.Save`)
гаргасан — гараар бичсэн fixture биш. Кодоос өмнө солилцох гаралт энэ.

Хэмжигдсэн зан төлөв:

1. **`formatVersion` бол файлын хамгийн эхний талбар.** Утга нь одоо `3`.
   Уншихад бүх файлыг задлах шаардлагагүй.
2. **`stageId` / `workPackageId` нь утгагүй үедээ `null`, хоосон мөр биш.**
   Хоёр уншигч хоёулаа `ValueKind == String` шалгадаг тул `null` нь
   хоосон мөр болж, аюулгүй. Гэхдээ энэ бол **санамсаргүй аюулгүй** байдал —
   гэрээнд бичигдээгүй байсан.
3. **Кирилл үсэг `\uXXXX` болж бичигддэг** (`"Барилга А"` →
   `"Бар..."`). `JsonElement.GetString()` буцаан задалдаг тул
   уншигчдад асуудалгүй. Харин файлыг **текстээр grep хийж болохгүй.**
4. Хамгийн бага төсөл ч ~500 мөртэй. Уншигч бүх файлыг задалдаг тул энэ нь
   зардлын хувьд ач холбогдолтой.
5. `albumStyle.cornerTable` нь анхдагчаараа **хоосон мөр** (`""`) —
   `AlbumCornerTableStyles.TemplateDecides`. «Утга байхгүй» биш, «загвар
   шийднэ» гэсэн утга.

### Хоёр формат — энэ баримтын анхны хувилбар хоёуланг нь буруу таасан

Файлын хоёр утга нь энгийн мөр биш, **формат**. Хоёуланг нь эхний ноорогт
таамагласан, PFR өөрийн уншигчийн бодит зан төлөвийг илгээхэд илэрсэн.
Бодит гаралт солилцох журам яг үүнийг барихын тулд байдаг.

**1. Барилгын бүлгийн metadata түлхүүр** нь `buildingGroupId` **биш**,
`source.buildingGroupId` (`ProjectDesignSourceClassification.cs:20`).

**2. `sheetBuildingAssignments`-ийн түлхүүр** нь хуудасны дугаар биш.
`SheetRecord.MakeKey` (`SheetLibrary.cs:28`) үүнийг ингэж зохиодог:

```
{эх сурвалжийн ялгагч}|{sheetId}      → бүхэлдээ ToLowerInvariant
```

Эх сурвалжийн ялгагч нь `sourceId`; **`sourceId` хоосон бол**
`{application}|{documentPath}` руу шилждэг — тэгвэл түлхүүр **гурван**
хэсэгтэй болно. Тиймээс PFR-ийн «`"{sourceId}|"` угтвараар хайх» арга зөв,
харин «`|`-ээр хоёр хуваах» арга буруу.

Жишээ: `revit-source-001|a-01`

Түлхүүр бүхэлдээ жижиг үсэгтэй. PFR том жижиг үсэг үл ялгаж харьцуулдаг тул
аюулгүй; Studio-гийн дотоод `BelongsToSource` нь `Ordinal` харьцуулдаг ба
энэ нь зөвхөн түлхүүр аль хэдийн жижиг үсэгтэй учраас ажилладаг.

Хоёулаа одоо STU талд тестээр бэхлэгдсэн — литералыг давтаж биш, Studio-гоор
өөрөөр нь үүсгүүлж.

### Enum нэр = утасны утга

`kind` нь `DesignSourceKind` enum-ийн **C# гишүүний нэр**:

```
Revit, AutoCad, CityGen, Pdf, Folder
```

PFR нь `"Revit"`-тэй яг тулгадаг (том жижиг үсэг үл ялгах).
PFA нь `-` `_` тэмдэгтийг хасаад `"AutoCad"`-тай тулгадаг.

Тиймээс **enum гишүүний нэр солих нь хоёр бүтээгдэхүүний утасны формат
солих явдал**. STU талд тестээр бэхлэгдсэн.

## Хувилбарын шалгалт — саналын гэрээ

### Одоогийн байдал

| Тал | Хувилбар шалгадаг уу |
| --- | --- |
| STU | **Тийм.** `ProjectWorkspaceStore.Load` нь `formatVersion > CurrentFormatVersion` үед `InvalidDataException` шиднэ |
| PFA | Үгүй |
| PFR | Үгүй |

Хоёр уншигч хоёулаа Studio-гийн ирээдүйн хувилбарын файлыг **өнөөдрийн
утгаар** уншина. Хэрэв v4-т жишээ нь `inboxFolder`-ийн утга харьцангуй зам
болвол хоёулаа буруу фолдер руу хардаг — алдаагүй, логгүй.

### Санал

Уншигч тал бүр дараах гурван мөрийг оруулна:

```csharp
// Studio бичдэг; байхгүй бол хуучин файл гэж үзнэ.
int formatVersion = root.TryGetProperty("formatVersion", out JsonElement v) &&
                    v.ValueKind == JsonValueKind.Number
    ? v.GetInt32()
    : 0;

if (formatVersion > SupportedProjectFormatVersion)   // одоогоор 3
{
    // Таамаглахгүй. Хэрэглэгчид Studio-гийн хувилбарыг хэлнэ.
    return Fail($"Энэ төслийн файл (формат {formatVersion}) нь энэ хувилбараас " +
                $"шинэ ({SupportedProjectFormatVersion}). Erk-S-ээ шинэчилнэ үү.");
}
```

Гурван дүрэм:

1. **Танихгүй бол татгалзана, таамаглахгүй.** Одоогийн чимээгүй эвдрэлийн
   эсрэг тал.
2. **Талбар байхгүй бол `0`, алдаа биш.** Дараагийн хэсгийг үз.
3. **Талбар нэмэх нь хувилбар өсгөхгүй.** Уншигчид танихгүй талбарыг
   алгасдаг тул additive өөрчлөлт тэднийг хөндөхгүй; хувилбар өсгөвөл
   шаардлагагүй газар зогсоно.

**STU-ийн баталгаа** (PFR-ийн шаардсан зүйл): байгаа талбарын **семантик**
өөрчлөгдвөл — жишээ нь `inboxFolder` үнэмлэхүй замаас харьцангуй зам болвол —
`CurrentFormatVersion` **заавал өснө**, мөн өсөхөөс өмнө PFA/PFR-т мэдэгдэнэ.
Тиймээс уншигч тал «хувилбар таарч байвал утгууд өнөөдрийнхтэй адилхан» гэж
найдаж болно. Энэ бол STU-ийн үүрэг: сайн санааны амлалт биш, дээрх талбарын
жагсаалт STU-ийн тестээр бэхлэгдсэн тул семантикийн өөрчлөлт нэрийн
өөрчлөлтгүйгээр анзаарагдахгүй өнгөрөх боломж багассан.

### Урхи: `formatVersion` байхгүй файл

STU-ийн `ProjectWorkspace.FormatVersion` талбар нь C# property
initializer-тэй (`= CurrentFormatVersion`). Тиймээс JSON-д талбар
байхгүй бол **хамгийн сүүлийн хувилбар гэж уншигдана**, `0` гэж биш.

Өнөөдөр хор хөнөөлгүй (доорх §«v2→v3-т юу өөрчлөгдсөн бэ»-г үз) боловч:

- Хувилбарын хаалгыг «талбар байгаа эсэх» дээр барьж болохгүй.
- STU-ийн репо доторх 8 `project.erksproject`-ийн **7 нь
  `formatVersion`-гүй** — бүгд гараар бичсэн fixture. Хэрэглэгчийн
  **18 бодит төслийн аль нь ч** versionless биш (доорхыг үз). Тиймээс
  fixture-үүдийг гэрээний нотолгоо болгож болохгүй: тэдгээр нь дискэн дээрх
  ямар ч бодит файлыг төлөөлдөггүй.

### `formatVersion: 2` гэж юу харагдсан бэ

PFR «бодит файлд `formatVersion = 2` байгааг харсан» гэж мэдэгдэв. Хоёр
удаа хэмжсэн — эхний хэмжилт **буруу байсан.**

**Эхний хэмжилт (буруу):** зөвхөн `E:\Erk-S Platform` доор хайж «v2
`.erksproject` байхгүй» гэж дүгнэсэн. Хайлтын хүрээ хэтэрхий нарийн байсан:
жинхэнэ төслүүд `Documents\Erk-S Platform\Studio Projects\` дор амьдардаг.

**Хоёр дахь хэмжилт (бүрэн), 18 бодит төсөл:**

| Байдал | Тоо | `formatVersion` |
| --- | --- | --- |
| Амьд төсөл | 15 | **бүгд 3** |
| `.old` архивласан хуулбар | 3 | **бүгд 2** |

Гурван v2 файл бүгд `.old`-оор төгссөн хавтсанд байна
(`…fresh-validation.old`, `…cloud-cache-before-fix.old`,
`…hydration-race-before-fix.old`) — алдаа мөшгих үед үлдээсэн хуулбарууд,

**Гурав дахь хэмжилт (PFR, бүх диск, 36 файл) — хоёулангийнх маань
тайлбарыг унагав.** PFR-ийн уншсан v2 файл нь **өөрсдийнх нь scratch

файлын дугаар» гэсэн тайлбар ч **буруу** — тэр файл `.erksalbum` биш байв.

Тэр сүүлчийн хэмжилтээс гарсан жинхэнэ олдвор:

> **`E:\Erk-S test\project.erksproject` → `formatVersion: 1`**
> (2026-07-16-нд бичигдсэн, түүнээс хойш нээгдээгүй)

STU тал бие даан баталгаажуулав: файл байна, v1, бүтэц нь жинхэнэ төслийнх
(`identity`, `cloud`, `foundation`, `deliverables` бүгд байна).

Тиймээс: **гурвуулаа өөр өөр буруу байсан** — PFR баримтаа буруу гаргасан,
би PFR-ийн алдааны шалтгааныг буруу таасан, ба зөв хариулт нь хоёр
тайлбарыг үл тоомсорлож **дискийг бүхэлд нь хэмжсэнээр** гарсан.

Харин **гарсан шийдвэр гурван удаа өөрчлөгдөөгүй**: хуучин хувилбарыг
хүлээж авах нь зөв. Одоо шалтгаан нь илүү хүчтэй болов — v1 файл **амьд**
байна, зөвхөн «онолын хуучин файл» биш. Studio хуучин файлыг зөвхөн
**дараагийн Save дээр** ахиулдаг тул хэрэглэгч нээгээгүй төсөл хэдэн ч
жил хуучин дугаартайгаа хэвтэнэ.

Энэ дүрэм ийм ачаа үүрдэг байтал **STU талд түүнийг барих тест байгаагүй**.
Одоо `AVersionOneFileStillOpens` v1 файлын бодит хэлбэрийг ачаалж,
түүнээс хойш нэмэгдсэн бүх зүйл `null` биш хоосон ирж байгааг шалгана —
ялангуяа `PrimaryAlbum`, энэ нь дутуу үед `null` буцаадаггүй, **шиддэг**.
Санаатай эвдэж баталгаажуулав (`Normalize`-ийн нөхөх салааг хааж) — тест
унав.

Нэг баримтад гурван удаа зөв дүгнэлтэд буруу замаар хүрлээ. Тиймээс замыг
нь ч бичив, зөвхөн дүгнэлтийг биш.

### v2→v3-т юу өөрчлөгдсөн бэ — PFA-гийн асуулт, ба нотолгооны хил

PFA зөв асуулт тавив: дүрэм тэгш бус (шинэ рүү хатуу, хуучин руу нээлттэй)
тул **хэрэв v2→v3 нь семантикийн өөрчлөлт байсан бол** v2 файлыг v3 гэж
уншиж байгаа нь яг бидний хаах гэж буй чимээгүй эвдрэл, зөвхөн нөгөө
чиглэлд. Тэгвэл доод хаалга ч хэрэгтэй.

**Git түүх хариулж чадахгүй.** `ProjectWorkspace.CurrentFormatVersion` нь
репогийн **хамгийн анхны коммитоос хойш 3 хэвээр** — 1→2 ба 2→3 шилжилт нь
түүхээс өмнө болсон. `CHANGELOG.md` ч форматын өсөлтийг бүртгээгүй. Diff
харуулах боломж алга.

**Файлууд юу хэлэв (дискэн дээрх бүх хуучин файл):**

| | Дээд түвшний түлхүүр | Шинээр нэмэгдсэн |
| --- | --- | --- |
| v1 | 11 | — |
| v2 | 13 | `creation`, `visualizations` |
| v3 | 24 | `albumStyle`, `boards`, `buildingGroups`, `portfolio`, `portfolioDocuments`, `recordDocuments`, `researchDocuments`, `sheetBuildingAssignments`, `siteContext`, `stageAssignments`, `stages` |

**v1 ⊂ v2 ⊂ v3.** Устгагдсан түлхүүр алга, нэр солигдсон нь ч алга.

**Гэхдээ энэ нотолгоо хамгийн чухал хэсэгт нь хүрэхгүй.** Дискэн дээрх
дөрвөн хуучин файл (v1 нэг, v2 гурав) **бүгд `"sources": []`** — хоосон.
Тэгэхээр `sources[]` доторх талбарын утга өөрчлөгдсөн эсэх талаар
**нотолгоо огт байхгүй**, ба яг тэр массив бол PFA/PFR хоёрын уншдаг зүйл.

Тиймээс энэ баримтын өмнөх «хувилбарууд зөвхөн талбар нэмсээр ирсэн» гэсэн
мэдэгдэл **нотолгооноосоо өргөн байсан**. Зөв томьёолол:

> Дээд түвшинд нэмэлт гэдэг нь **батлагдсан**. `sources[]` доторх семантик
> өөрчлөгдсөн эсэх нь **шалгагдаагүй** — шалгах материал байхгүй.

**STU-ийн хариулт: доод хаалга нэмэхгүй.** «Нэмэлт гэдэг батлагдсан» учраас
биш — **доод хаалгыг баталгаажуулах боломжгүй** учраас. Хэрэв PFA/PFR v2-ыг
татгалзвал өнөөдөр дискэн дээр байгаа v2 файлуудыг татгалзана; тэдгээр нь
`sources` хоосон тул буруу уншигдах зүйл огт байхгүй. Таамгийн үндсэн дээр
ажиллаж байгаа файлыг татгалзах нь бодит эрсдэлээс том хохирол.

**Оронд нь: хэмжигдээгүй хослолыг дохио болго.** Эрсдэл нь «v3-аас өмнөх
файл» биш, «v3-аас өмнөх файл **бөгөөд `sources` хоосон биш**» — тэр
хослолыг хэн ч хэзээ ч хараагүй. Уншигч тал түүнтэй таарвал татгалзалгүйгээр
**тэмдэглэж мэдээлбэл** тодорхойгүй байдал таамаг хэвээр үлдэхийн оронд
баримт болно. Тэр өдөр гурвуулаа шийднэ.

### `.erksalbum` нь өөр дугаартай

Энэ нь дээрх PFR-ийн тохиолдлын тайлбар **биш** (тэр таамаг буруу байсан),
харин тусдаа бодит урхи. Studio өөрөө бичсэн төслийн хавтас дотор хоёр
файл зэрэг байна:

```
project.erksproject                              → "formatVersion": 3
albums/building-architecture-concept.erksalbum   → "formatVersion": 2
```

`.erksalbum` бол **өөр баримт, өөрийн хувилбарын дугаартай**
(`StudioAlbumDocument.CurrentFormatVersion = 2`). Хоёр дугаар хоорондоо
хамааралгүй, тус тусдаа өснө. Уншигч тал дэмжих дээд хувилбараа үүн дээр
тулгуурлан тогтоовол буруу тоо авна. PFR энэ урхийг өөрсдийн талд файлын
түвшинд шалгаад тестээр хаасан: альбомын файлыг төслийн уншигчид өгвөл
binding гарахгүй, «эвдэрсэн» гэж ч мэдээлэхгүй.

Кодод нь илүү муу: **`CurrentFormatVersion` нэртэй гурван тогтмол** байна —
`ProjectWorkspace` (3), `StudioAlbumDocument` (2), `AlbumProject` (2, хуучин
альбом). PFR хайж байгаад эхлээд буруу нь дээр таарсан. Гурвуулаа одоо
`RaisingTheProjectFormatVersionIsAThreeProductChange` тестэд **хамт**
бэхлэгдсэн — уншигч гурвууланг нь нэг дор хараад алийг нь хэрэглэхээ мэднэ.

Мөн тэр тест PFR-ийн саналын дагуу анкер болно: `ProjectWorkspace`-ийн
дугаарыг өөрчилсөн хүнд «PFA/PFR-т эхлээд хэл» гэж хэлнэ. **Амлалт бол
механизм биш**, өөрчлөлт нь STU-гийн кодод болдог тул сануулга ч STU-д
байх ёстой.

## Техник шийдвэр — PFA/PFR-тэй тохирох зүйл

Мастерын даалгавар: «нэг файл хуваалцах уу, гэрээгээр тэгшлэх үү — техник
шийдлээ PFA/PFR-тэй тохир».

STU-ийн санал: **гэрээгээр тэгшлэх**, нэг файл хуваалцахгүй. Шалтгаан:

1. Уншигчийн гадаргуу нь 17 талбар — хуваалцсан кодын зардлыг
   зөвтгөхөөргүй жижиг.
2. PFA нь AutoCAD-ийн дотор, PFR нь Revit-ийн дотор ажилладаг. Хоёр өөр
   host, хоёр өөр .NET, хоёр өөр deploy. Хуваалцсан файл гурав дахин
   хуулагдана — өнөөдрийн давхардлаас ялгарах зүйлгүй.
3. Хуваалцсан код нь **STU-ээс хамаарал үүсгэнэ**. Одоо PFA/PFR хоёр
   Studio-гийн файлыг уншдаг ч Studio-гийн кодоос хамаардаггүй. Энэ бол
   давуу тал, алдагдуулах шаардлагагүй.

Оронд нь:

- STU дээрх талбарын жагсаалтыг тестээр бэхэлнэ (**хийгдсэн**).
- PFA/PFR тус бүр дээрх 3 мөрийн хувилбарын хаалгыг оруулна.
- Гурвуулаа `SupportedProjectFormatVersion = 3` гэж өөрийн талдаа
  тогтмолоор зарлана.
- STU `CurrentFormatVersion`-ыг өсгөхөөс **өмнө** PFA/PFR-т мэдэгдэнэ.

### PFR-ийн эсрэг санал: «хуваалцсан код бол хувилбарын шалгалт нэг газар амьдарна»

Зөв ажиглалт, гэхдээ энэ нь **асуудлыг зөөнө, шийдэхгүй**. Хуваалцсан эх код
гурван хостод гурван удаа compile хийгдэж, гурван өөр цагт deploy хийгдэнэ.
Тэгвэл PFA-д v3-ын шалгалттай хувилбар, PFR-д v2-ынх зэрэг ажиллах бүрэн
боломжтой — «нэг газар» гэдэг нь эх кодод л үнэн, ажиллаж байгаа систем дээр
биш. Харин тэр үед хоёулаа нэг файлаас гаралтай учир **зөрүү нь харагдахаа
болино**: «хуваалцсан код тул адилхан» гэж таамаглах болно.

Гурван мөрийн шалгалт нь эсрэгээрээ ил байна. Тэр гурван мөрийг PFA/PFR тус
бүрдээ уншиж, өөрсдийн дэмжих хувилбараа өөрсдөө зарлана.

Хэрэв PFA эсвэл PFR энэ саналтай санал нийлэхгүй бол код бичихээс өмнө хэлнэ
үү. PFR аль алинд бэлэн гэдгээ хэлсэн; PFA-гийн санал хараахан ирээгүй, тэр
ирэхээс өмнө хэн ч хэрэгжүүлж эхлэхгүй байхыг хүсье.
